日期：2026-10-30。状态：D05/D08/D09 的本机可控故障小阶段已验证，完整 P0 未完成。
本轮为 macOS 可控故障验收，Windows 实机继续延后，用户真实材料仍待开发完成后提供。

## 实现与边界检查

- `StepRecovery` 在服务端限制每阶段恢复次数与累计活动时间，定位失败后要求新快照，成功不重置次数，暂停不消耗预算。
- `MutationFence` 防止未确认操作后的追加写入，并以不包含按钮文字的稳定目标信息限制重复点击；按键使用真实焦点而非模型声称的目标。
- 定位失败只在动作发出前恢复。调用已发出却丢失回执时，记录步骤 UNCERTAIN、用例 ERROR，最多补采一轮只读快照/截图后结束；不改原始步骤和预期。
- `.env` 默认恢复 2 次、累计活动时间 120 秒；示例 JSON 不自动加载。
- 对独立状态规则先写失败测试，确认实现缺失导致失败后补实现；5 项预算/写操作状态检查通过。
- `pnpm test`：50 项通过；`pnpm typecheck` 通过；`pnpm build` 通过，保留既有 Radix `use client` 非阻塞警告。前端只补“结果不确定”文案，没有调整一屏布局。

## 真实联调方法

`pnpm recovery:check --scenario=recover|exhaust|time-limit|uncertain`：使用真实模型、Pi、已安装 MCP 与本机 Chrome。独立 SQLite/确认后的合成 xlsx 位于 `data/recovery-check/`，与用户任务共享浏览器锁；不修改用户已有环境，不手动启动或重启服务。

故障由验收专用的 `McpClient` 子类注入，API、环境配置和工作簿没有开启故障的能力：

- 定位故障将动作前的目标读取交给真实 MCP 解析一个不存在的目标，保留实际工具错误；后续由模型取快照并重新选择目标。
- 回执丢失先让真实 MCP 点击并获得成功返回，再由验收调用层丢弃该返回。执行器不知道点击是否生效，必须保守退出；原生返回成功只作为验收侧审计，不写成用例通过。
- 页面每次实际点击会调用自己的合成目标创建接口。执行器仍只操作 UI；脚本最后读取计数仅用于检查副作用次数，不替代 UI 步骤或预期证据。
- `exhaust` 使用 300 秒恢复窗口隔离次数上限；`time-limit` 使用 1 秒窗口隔离时间上限；其他场景使用默认 120 秒。

## 联调发现的计时器问题

并发工具都在 `await control.boundary()` 前清除旧计时器，返回后各自新建；后一个覆盖变量，前一个无法在 finally 清理，命令因此可能等待残留的单用例计时器。已在 await 之后、重新挂计时器之前再次清除当前计时器。

对同一边界函数做两路并发的受控调度对照：旧逻辑挂起 2 个，收尾后遗留 1 个；修正后只保留 1 个，收尾后为 0。诊断摘要 `data/recovery-check/timer-reproduction.json`。这只证明计时器机制，真实 CLI 自然退出仍需下列后续联调确认，不通过强制 `process.exit` 掩盖收尾。

回执丢失任务 `066a2af5-b55b-4037-bccb-9923e77d16d7` 已自然退出 0：真实 MCP 点击后注入回执丢失，首条 ERROR、步骤 DONE/UNCERTAIN，后续用例 PASSED；真实创建 1 次、原生点击 1 次。只读快照与截图显示“创建完成”“本窗口提交次数：1”，按钮文字已经变为“再次创建记录”，执行器仍未重新点击或改用回车。执行器未因验收侧知道创建成功而将用例记 PASSED。工具进程和锁释放。
