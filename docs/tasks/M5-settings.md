## 配置项与 Pi 真实字段对照

| 页面字段 | Pi SDK 字段 | 说明 |
|---|---|---|
| 显示名称 / 模型 ID | `name` / `id` | 原样注册 |
| 接口地址 | `baseUrl` | 校验 HTTP(S)、拒绝内嵌凭证 |
| 上下文窗口 | `contextWindow` | 1024–2,000,000 |
| 最大输出 token | `maxTokens` | 256–1,000,000，且不得超过上下文窗口 |
| 输入类型 | `input: ('text'|'image')[]` | 文本强制开启；关闭图像时验证码类预期会明确失败 |
| 推理 | `reasoning` | 关闭时思考档位锁定 `off` |
| 思考档位 | `thinkingLevel` | `off/minimal/low/medium/high/xhigh/max`，原样传给会话 |

默认值与改造前的硬编码值完全一致（65536 / 4096 / text+image / false / off），未配置的提供商行为不变。

## 存储与安全

提供商记录存 `documents('model-provider')`，API 密钥单独 AES-256-GCM 存在 `data/credentials/`，记录里只留 `credentialRef`，任何页面响应都不下发密钥或引用。启用状态是单例记录 `('model-active','active')`，内部保存 `providerId`，与提供商记录分离，避免两份 active 表示不一致。

实现中修正的真实缺陷：
- `active` 状态曾同时存在「记录字段」与「单例键」两份表示，删除激活项后不同步；改为单一真源。
- 激活记录读写键不一致（写 UUID、读 `'active'`），导致首个提供商无法自动启用。
- 密钥用 `JSON.parse` 解码，但 `password()` 存的是裸字符串，导致读取失败。
- 改造前保存的提供商记录缺少新字段，`resolveModelConfig` 会算成 `input: []`，模型声明不支持任何输入而彻底不可用；已改为逐字段回落默认值，并有回归测试锁定。
